## Overview

A fully automated pipeline built on n8n that monitors Google Drive folders for new video uploads, generates SEO-optimised YouTube metadata using AI, uploads the video, and notifies via Telegram — all without manual intervention.

Designed for small-volume, multi-channel publishing (1-2 videos per day per channel).

Hosted on a dedicated DigitalOcean droplet running n8n self-hosted (Community Edition).

## API Quota — Important

YouTube Data API v3 quota is 10,000 units per day per Google Cloud project. A video upload costs 1,600 units. A metadata update costs 50 units. That gives roughly 6 uploads per day per project.

The quota is tied to the GCP project, not the YouTube channel. If all channels share one project, they share one 10,000-unit pool. To avoid this, create a separate GCP project for each channel. Each project gets its own isolated 10,000-unit allocation.

At 1-2 videos per channel per day, this is comfortable headroom. No quota increase request needed.

Quota resets at midnight Pacific Time daily.

## Edge Cases Handled

| Scenario | How It's Handled |
|---|---|
| Duplicate upload (same filename) | Google Sheets log check — skips if already processed |
| MP4 uploaded without TXT | IF node detects missing match -> Telegram alert -> workflow stops cleanly |
| Two videos uploaded at same time | n8n queues executions — processes one at a time |
| Video goes Public accidentally | All uploads default to Private — manual publish step required |
| OAuth token expiry | n8n handles token refresh automatically in most cases |
| Poor quality transcript | AI output reflects input quality — set expectations with uploaders |
| Large video file timeout | Binary data mode set to filesystem; payload size limit increased (see env vars) |
| MIME type rejection (400 error) | Code node forces binary MIME type to video/mp4 before upload |
| Upload succeeds but AI/metadata fails | YouTube video ID is logged to Sheets immediately after upload, before AI runs — orphan videos are recoverable |
| Mid-execution crash (memory, network) | Dedicated n8n error workflow sends Telegram alert with execution ID and failed node |
| Quota exceeded (too many uploads) | 403 quotaExceeded error — separate GCP project per channel prevents cross-channel exhaustion |
| Disk fills up over time | Code node deletes local MP4 binary after successful upload and YouTube video ID verification — keeps droplet disk clean |

## n8n Environment Variables Required

These must be set on the DigitalOcean droplet's n8n Docker config to handle large video files without crashing:

N8N_DEFAULT_BINARY_DATA_MODE=filesystem
N8N_PAYLOAD_SIZE_MAX=1600

filesystem mode writes binary data to disk instead of holding it in memory. Without this, large MP4s will crash the workflow. PAYLOAD_SIZE_MAX is in MB — set to at least the size of your largest expected video file.

## The goal

A YouTube auto-uploader for multiple channels, triggered by editors sending messages to a Telegram bot. Editor pastes a Google Drive link to the MP4 + the transcript as a text message. Bot uploads the MP4 to YouTube as Private, generates AI metadata (title / description / tags) from the transcript, patches the video, logs to Google Sheets, replies with the YouTube link.

Editors are a trusted, whitelisted group. One bot handles all channels.

---

## Why we pivoted away from Drive polling

The original design polled Drive folders for new MP4 + matching TXT pairs. Two problems killed it:

1. **Race condition.** Editor drops MP4 at 11:00:30, TXT at 11:01:30. Polling at 11:01:00 catches MP4 alone → fires "missing TXT" alert → TXT lands orphaned.
2. **No explicit "ready" signal.** Editor might be mid-upload, might have uploaded to wrong folder, might have forgotten the TXT. Polling assumes intent from file presence.

Bot trigger fixes both: editor explicitly signals readiness by sending the message. The message **is** the trigger. No ambiguity.

## Editor flow (the design, finalized)

Three-step conversation per video:

**Step 1** — editor starts:
```
/upload wiserice
```

**Step 2** — bot replies:
```

```

Editor sends:
```

```

**Step 3** — bot replies:
```

```

Editor sends the full transcript as a text message.

**Step 4** — bot replies:
```

```

Bot runs the pipeline in background. When finished, bot replies:

## Technical design details

### Drive link parser

Accept any of:
- `https://drive.google.com/file/d/FILE_ID/view?usp=sharing`
- `https://drive.google.com/file/d/FILE_ID/view`
- `https://drive.google.com/open?id=FILE_ID`
- `https://drive.google.com/uc?id=FILE_ID`
- bare `FILE_ID`

Implementation: regex for `/d/([a-zA-Z0-9_-]+)` and `[?&]id=([a-zA-Z0-9_-]+)`, fallback to `[a-zA-Z0-9_-]{20,}` for bare IDs. Validate the extracted ID actually resolves in Drive before proceeding (call `get_file_metadata`).

### Which Drive account does the bot use?

The bot needs to read the MP4. Simplest model: **one shared "bot Drive account"** whose OAuth token is at `tokens/token_drive.json`. Editors share their upload folders (or individual files) with that account's email. Bot reads from wherever the shared file lives.

**Why not use per-channel tokens for Drive?** Editors might work across channels, upload to their own drives, etc. A shared reader account is simpler.

**YouTube tokens are still per-channel** — each YouTube channel needs its own OAuth token at `tokens/token_<channel>.json` for the upload step. No change there.

### Authorization check

Every message from a non-whitelisted user gets a flat "not authorized" reply. Every `/upload <channel>` checks the editor is approved for that specific channel.

### Concurrency

Per-user: only one active conversation at a time (ConversationHandler enforces this naturally).

Globally: uploads run in background tasks via `asyncio.create_task`. Pipeline already handles retries + errors internally. No explicit queue needed for v1 — if 5 uploads fire at once, they run in parallel. YouTube quota per-channel is ~6 uploads/day; parallelism is fine.

v2 improvement (not in scope now): a proper queue if we ever need throttling.

### Background upload + progress updates

```python
async def start_upload_task(channel, file_id, transcript, chat_id, bot):
    async def notify(msg):
        await bot.send_message(chat_id=chat_id, text=msg)
    try:
        await run_pipeline(channel, file_id, transcript, notify)
    except Exception as e:
        await notify(f"❌ Failed: {e}")
        # also ping admin
        await bot.send_message(chat_id=ADMIN_CHAT_ID, text=f"[{channel}] crash: {e}")
```

### State / dedup

`state.py` still used — keyed by Drive `file_id`. If an editor sends the same link twice, bot replies "Already uploaded on <date> → <YouTube URL>" and doesn't reprocess.

### Systemd

`yt_uploader.service` doesn't change — same `ExecStart`, just runs the new `main.py`.

6. Bot survives network flake, restart, and OAuth token refresh without manual intervention.
7. Systemd restarts the bot on crash.

Yeah, n8n has a native Google Drive Trigger node — that's what the plan is already using (step 1 in the node list).

How it works:

Point it at a specific folder (e.g. the channel's upload folder)
Event: "File Created"
Filter by MIME type = video/mp4
It polls Drive's API on an interval you set (1 min, 5 min, etc.)
So it's not a true push/webhook — it's polling under the hood. Drive does have a proper push API (files.watch) that sends real webhooks, but n8n's built-in node doesn't use it. For this use case polling is fine — nobody cares if the upload starts 60 seconds later.

A few practical notes:

Polling interval matters for the TXT race condition. If you poll every 1 min and uploader drops MP4 then TXT within that window, both show up in the same poll — no race. If MP4 lands at 11:00:30 and TXT at 11:01:30, MP4 gets picked up alone at 11:01:00 poll → alert fires → TXT arrives orphaned. So either:

Set poll to 2-5 min (gives uploader buffer time), or
Add a "wait 90s then re-check for TXT" branch before alerting
Trigger fires on partial uploads too. Drive marks the file as "created" when upload starts, not when it finishes. For a 1GB video this matters — you can trigger on a half-uploaded file. Mitigation: check file.size stability, or have the Download node retry on failure, or poll less aggressively so upload finishes between polls.

Trigger only sees what it has permission to. Make sure the Google account running the n8n credential has access to the folder. Sounds obvious but bites people with shared drives.

Alternative if you ever want real-time: Drive push notifications → webhook node in n8n. More setup (domain verification, channel renewal every 7 days max), not worth it here.

That's it. Every 2 minutes, for every channel, it asks Drive "any MP4s in this folder?" via drive.list_mp4s(). If yes, checks SQLite — already processed? skip. Not processed? check for matching TXT. Both present? go.

So the "trigger" is: the script itself running continuously + a Drive API call every 2 min.

That's why it needs systemd (the yt_uploader.service file) — so the loop keeps running forever. systemctl enable --now yt_uploader = "start it now and restart on boot / on crash."

Why polling, not webhooks:

Drive does support real push notifications (files.watch API). But:

Needs a public HTTPS endpoint on your droplet (domain + SSL cert)
Channels expire every 7 days max — you'd need renewal logic
For uploads-per-day volume, 2-min polling latency is invisible
n8n's Drive Trigger polls too. You're not losing anything.

What you can tune in .env:

POLL_INTERVAL_SEC=120    # how often to check Drive (lower = more API calls)
TXT_GRACE_SEC=180        # how long to wait for TXT before alerting
If you want faster reaction, drop POLL_INTERVAL_SEC to 60. Drive API allows way more than that — you'll be nowhere near quota at 1 call/min/channel.

If you want it to really feel instant: there's no free way. Webhooks need a domain. Not worth it for your use case.

oh that's actually a better design. Genuinely. Let me tell you why before I get too excited:

Why this is smarter than polling Drive
1. No race condition. Editor uploads MP4 + TXT to Drive, waits till both are done, sends you one Telegram message. No grace period guessing, no "TXT arrived 90 seconds late" problem. The editor confirms readiness by the act of sending.

2. Instant trigger. Telegram bots get webhook-style push. No 2-min polling lag.

3. Explicit workflow. Right now Drive polling is implicit — editor might be mid-upload, might have forgotten the TXT, might have uploaded to the wrong folder. With a bot, the editor signals intent: "this one's ready, ship it."

4. Multi-editor friendly. Each editor has their own Telegram. They just DM the bot. You can route by who sent it (user_id → channel mapping).

5. Editors can send context. "here's the file, title should emphasize X." Free metadata hint to feed into the AI prompt.

6. No Drive folder management. No "which folder watches which channel." The Telegram message carries the channel.

The tradeoffs (real ones)
1. Editors have to do one extra step. Upload → copy link → paste in Telegram. Not automatic. For trusted editors this is fine. For flaky ones it's a new place to forget.

2. You need Drive link parsing. Editors might paste:

https://drive.google.com/file/d/FILE_ID/view?usp=sharing
https://drive.google.com/open?id=FILE_ID
a folder link (needs MP4+TXT inside)
just the file ID
Handle all of them. Not hard, just real.

3. Permissions. The bot's service account needs read access to whatever the editor shares. Either:

editor uploads to a shared Drive your account already accesses (same as before), or
editor shares the file with your service account email (extra step for them)
4. Bot security. Anyone who finds your bot can spam it. Whitelist user_ids in config — only approved Telegram accounts can trigger uploads.

5. What does the editor send, exactly? Design choice:

Option A: one Drive link to a folder → bot finds MP4 + TXT inside
Option B: two links in one message (MP4 link + TXT link)
Option C: link to MP4 + TXT pasted as message body (no separate file)
Option D: editor uploads MP4 to Drive, sends link + types transcript directly in Telegram
Option C is actually really clean — transcript is just text, no reason it needs to be a file. Editor sends:
